# 06 · 事件系统

事件用于在系统之间传递**临时性、一次性的消息**，例如"玩家按下了跳跃键""子弹击中了目标""任务完成"。事件与组件/资源的核心区别是：**事件只在当前 tick 内存活，tick 结束时自动清空**。

## 设计思想

PureEcs 的事件模型借鉴 Bevy：

- **类型化**：每种事件是一个组件类型（普通 class），`Events<T>` 通道按类型独立存储；
- **发布/订阅解耦**：发送方不需要知道谁在听，接收方不需要知道谁发的；
- **游标（cursor）读取**：每个 `EventReader` 用独立的 `lastId` 游标记录"我已经读到哪条"，因此：
  - 同一种事件可以有多个 reader，各自从上次位置继续；
  - reader 不会重复读到自己已经消费过的条目；
  - 系统先写后读、跨系统分发都安全；
- **每 tick 清理**：tick 结束时 `Events.clear()` 清空所有条目，事件天然"只在当前帧有效"。

> 相比"用组件做信号"（写一个标记再让别的系统清除），事件让代码意图更清晰，也避免组件被当临时变量用。

## 注册事件

在 `App`（或 `World`）上先注册事件类型，之后才能用：

```ts
import { App, World } from 'pureecs';

class PlayerJumped { constructor(public playerId = 0) {} }
class BulletHit { constructor(public target = 0, public damage = 10) {} }

const app = new App()
  .addEvent(PlayerJumped)
  .addEvent(BulletHit);
```

- `World` 同理：`world.initEvent(PlayerJumped)`（内部若未注册会自动按需创建通道）。
- 事件类是普通 class，可携带任意数据。

## 发送事件：EventWriter

在系统参数里声明 `EventWriter(T)`，得到带 `.send(event)` 的 writer：

```ts
import { App, World, params, Query, EventWriter, EventReader } from 'pureecs';

class PlayerJumped { constructor(public playerId = 0) {} }
class PlayerId { constructor(public id = 0) {} }
class CanJump {}

// 任何系统都可以"发布"事件：
const jumpInput = params(Query(PlayerId, With(CanJump)), EventWriter(PlayerJumped))
  .system((players, writer) => {
    for (const [p] of players) {
      if (p.id > 0) {
        // 满足条件就发送事件（这里简化为无条件，实际可判输入/冷却等）
        writer.send(new PlayerJumped(p.id));
      }
    }
  });
```

> 核心就一句话：`writer.send(new PlayerJumped(...))`。条件判定完全由你决定。

> 事件发送没有数量/时间限制；同一 tick 发送多条会被 reader 依次读到。

## 接收事件：EventReader

声明 `EventReader(T)` 后调用 `.read()` 得到**本 tick 新增**（自上次读取以来）的事件数组：

```ts
class PlayerJumped { constructor(public playerId = 0) {} }

const sfxSystem = params(EventReader(PlayerJumped)).system((reader) => {
  const jumps = reader.read();   // PlayerJumped[]
  for (const jump of jumps) {
    playSound('jump', jump.playerId);
  }
});
```

### 双系统一帧内"写后读"

由于同 tick 内发送的事件立即可被读，一个系统发、另一个系统读的"流水线"很常见。**同一系统的 `EventWriter` 与 `EventReader` 也能共存**：

```ts
// 系统内部：先响应输入发"跳"事件，再消费同帧其它来源的"跳"事件
const inputAndReact = params(
  ResMut(KeyboardInput),
  EventReader(PlayerJumped),
  EventWriter(PlayerJumped),
).system((input, reader, writer) => {
  if (input.justPressed(KeyCode.Space)) {
    writer.send(new PlayerJumped(playerId));
  }
  for (const jump of reader.read()) {
    applyJump(jump.playerId);
  }
});
```

### 游标语义与"没读到"

`EventReader` 是 **per-系统实例** 的（每次 `params()` 创建 reader，闭包里维护自己的 `lastId`）。因此：

```ts
const a = params(EventReader(Hit)).system((r) => r.read()); // 读到全部
const b = params(EventReader(Hit)).system((r) => r.read()); // 也读到全部（各自游标独立）
```

## 发送者与接收者的执行顺序

事件是**每 tick 清理**的临时数据，因此"哪个系统先跑"决定了 reader 能否在同一 tick 内读到刚发送的事件。准确语义如下：

1. tick 开始时，`Events` 通道是空的（上一 tick 末尾已 `clear()`）；
2. 系统按调度顺序执行，谁调用了 `send()`，事件立即进入通道；
3. 某系统执行 `read()` 时，读到**截至此刻本 tick 已发送**、且 id 大于自己游标的事件；
4. **tick 结束**执行 `Events.clear()`，本 tick 尚未被任何 reader 消费的事件被丢弃。

由此推出三条使用法则：

- **同一 tick 内"发送→接收"是可行的**：只要发送系统排在接收系统**之前**（注册顺序或 `before` 约束），后一个系统立刻能 `read()` 到。这是标准流水线玩法，也是推荐做法。
- **若接收系统排在发送系统之前**：它这一 tick 读不到，而事件在 tick 末被清空 → **该事件就此丢失**。所以依赖事件时务必安排好顺序。
- **不要用事件传递"持久状态"**：事件不是资源，漏掉一帧就没了。

```ts
// 推荐结构（发送系统在前）：
// detectDeath → uiSystem → printMessages
// PlayerDied  事件：detectDeath 发送，uiSystem 与 logSystem 各自用独立游标读到；
// ShowMessage 事件：uiSystem 发送，printMessages 读到。
```

**实践结论**：把"产生事件的系统"排在"消费事件的系统"前面（注册顺序或 `before`/`inSet` 约束，见 docs/08），形成稳定的发布-订阅流水线即可。

## 用 Commands / World 发送

不想用 `EventWriter` 参数时，也可以直接往世界通道发：

```ts
// 系统外任意时机：
world.getEvents(PlayerJumped)?.send(new PlayerJumped(7));
```

更常见的是在 `Commands` 之外，世界 API：

```ts
app.addSystem((world) => {
  world.getEvents(PlayerJumped)?.send(new PlayerJumped(1));
});
```

`getEvents` 返回 `Events<T> | undefined`（未注册时 undefined）；`getRequiredEvents` 在缺失时抛错。

## 完整可运行示例

```ts
import { App, World, params, Query, EventWriter, EventReader } from 'pureecs';

class Player { constructor(public id = 0, public alive = true) {} }
class PlayerDied { constructor(public id = 0) {} }
class ShowMessage { constructor(public text = '') {} }

function setup(world: World) {
  // 开局一个"已死亡"的玩家，让 detectDeath 每 tick 都能产出 PlayerDied 事件
  world.spawnWith(new Player(1, false));
}

// 生产者：把死亡玩家变成事件
const detectDeath = params(Query(Player, EventWriter(PlayerDied))).system((players, writer) => {
  for (const [p] of players) {
    if (!p.alive) writer.send(new PlayerDied(p.id));
  }
});

// 消费者 1：UI
const uiSystem = params(EventReader(PlayerDied), EventWriter(ShowMessage)).system(
  (reader, msgWriter) => {
    for (const died of reader.read()) {
      msgWriter.send(new ShowMessage(`player ${died.id} died`));
    }
  },
);

// 消费者 2：记日志（独立游标，同一事件它也会读到）
const logSystem = params(EventReader(PlayerDied)).system((reader) => {
  for (const died of reader.read()) {
    console.log('log: player', died.id, 'died');
  }
});

// 消费者 3：显示消息
const printMessages = params(EventReader(ShowMessage)).system((reader) => {
  for (const m of reader.read()) console.log('UI:', m.text);
});

new App()
  .addEvent(PlayerDied)
  .addEvent(ShowMessage)
  .addStartupSystem(setup)
  .addSystem(detectDeath)
  .addSystem(uiSystem)
  .addSystem(logSystem)
  .addSystem(printMessages)
  .run(2);
```

## 事件 vs 组件 vs 资源：怎么选

| 数据形态 | 用哪个 | 原因 |
| --- | --- | --- |
| 一次性信号，当前帧有效 | **事件** | tick 结束自动清空，无需手动清理 |
| 持续存在、需要被查询/过滤 | 组件 | 组件是实体的持久属性 |
| 全局唯一、跨系统共享 | 资源 | 见 docs/07 |
| 需要延迟、跨 tick 稳定 | 资源 或 持久组件 | 事件每 tick 丢 |

## 小结

- 事件类型 = 普通 class，需先 `addEvent` / `initEvent` 注册；
- `EventWriter(T).send(v)` 发布；`EventReader(T).read()` 消费（自带游标，不会重复读）；
- 事件只在当前 tick 内有效，tick 末自动清空；
- 同 tick"写后读"可行，但**消费方要排在发送方之后**（用调度排序）；
- 系统外可用 `world.getEvents(T)?.send(...)`。
