# 11 · 性能最佳实践

PureEcs 在架构上已经为游戏/模拟场景做了不少优化（SparseSet、最小候选集、引擎缓存、零分配快路径），但**最终性能仍然取决于你怎么使用**。这篇总结从"内部机制 → 你能做的取舍"讲清楚。

## 先理解内部三件套

### 1) SparseSet 组件存储

`World` 为**每个组件类型**维护一个 SparseSet（sparse 映射实体 ID → dense 下标，dense 顺序存组件实例）：

- 插入 O(1)（均摊），删除 O(1)（swap-remove 后移动尾部元素填空）；
- 遍历组件 = 遍历 dense 数组，缓存友好；
- **删除会移动元素**——这就是为什么遍历中拿到的引用不能长期保留（见下）。

```ts
// dense 数组的组件实例就是查询/遍历给你引用的对象。
// despawn 或 removeComponent 之后，它可能被 swap-remove 移走/覆盖。
```

### 2) 查询引擎 = 最小候选集 + 缓存

`Query(A, B, With(Rare), ...)` 的执行逻辑：

1. 找出**候选者最少**的那个 storage 作为遍历起点（"最小组件集"原则：拿稀有的当外层，避免遍历海量实体再做排除）；
2. 其余 fetch/filter 只做 `get(entityId)` 存在性检查；
3. `QueryEngine` 按 World 缓存解析好的 storage 引用；仅当世界出现**新的组件类型**（`storageVersion` 递增）才重建缓存。

带来的结论：

- 让系统"想要什么就声明什么"，不要手动遍历全实体再 if 判断——查询引擎会替你选最短路径；
- 同一 World 上重复使用同一 `Query`，第二次开始基本没有额外解析开销；
- **频繁新定义组件类型会令缓存失效**（少见，但动态创建 class 不是好主意）。

### 3) 每 tick 的自动清理

- Commands 在**每个 Stage 结束后**统一应用；
- 变更追踪（Added/Changed）与事件通道在 **tick 末尾**清空。

## 实战建议（按收益排序）

### ① 遍历用 systemForEach（零分配）

`system()` 会为每个参数分配数组/元组。`systemForEach()` 逐实体回调、无中间数组，是最快的常规遍历：

```ts
// 好：不分配结果数组
params(Query(Position, Velocity)).systemForEach((pos, vel) => {
  pos.x += vel.x;
});

// 可以：会分配 rows 数组（表达能力更强，适合多查询/组合）
params(Query(Position, Velocity)).system((rows) => {
  for (const [pos, vel] of rows) pos.x += vel.x;
});
```

限制回顾（docs/03）：`systemForEach` 只接受**单个 `Query()`**；想同时用资源/命令/多个查询 → `system()`。

### ② 大批量创建用 spawnWith 批量挂组件

`spawn()` 之后逐个 `insertComponent` 会为每个组件重复"实体 ID → 组件 ID 表"查改。`spawnWith(...)` 一次性带上全部初始组件，内部合并处理，**快得多**：

```ts
// 差：一批 1000 个实体逐个插 3 个组件
for (let i = 0; i < 1000; i++) {
  const e = world.spawn();
  world.insertComponent(e, new Position(i, 0));
  world.insertComponent(e, new Velocity(1, 0));
  world.insertComponent(e, new Sprite('s'));
}

// 好：一次搞定
for (let i = 0; i < 1000; i++) {
  world.spawnWith(new Position(i, 0), new Velocity(1, 0), new Sprite('s'));
}
```

### ③ 不要在系统内/回调里长期持有组件引用

SparseSet 的 swap-remove 会让 dense 数组里的元素"搬家"：

```ts
// ✗ 危险：把回调拿到的 pos 引用存起来，稍后用
const cache = new Map<number, Position>();
params(Query(Position, Entity)).system((rows) => {
  for (const [pos, entity] of rows) cache.set(entity.id, pos);
});
// → 之后其它实体 despawn/remove 后，cache 里的 pos 可能已被复用/覆盖

// ✓ 安全：只在回调内同步使用；跨帧需要"位置"就复制一份值对象
params(Query(Position, Entity)).system((rows) => {
  for (const [pos, entity] of rows) {
    if (wantsToTrack(entity)) {
      snapshot.set(entity.id, { x: pos.x, y: pos.y }); // 深拷贝值
    }
  }
});
```

### ④ 合理利用 Local 做跨帧缓存

把"每帧都会重建的临时对象"放进 `Local`：

```ts
// 差：每帧 new 一个数组 + 一个临时对象（如果值其实可以复用）
params(Query(Position)).system((rows) => {
  const tmp = new Set<number>();
  for (const [pos] of rows) tmp.add(pos.x | 0);
});

// 好：跨帧复用（注意 tick 内要自清理）
params(Query(Position), Local(() => new Set<number>())).system((rows, seen) => {
  seen.clear();
  for (const [pos] of rows) seen.add(pos.x | 0);
});
```

> `Local` 工厂只在首次执行创建一次（docs/03），适合数组池、Set、统计对象。

### ⑤ 查询里 fetch 尽可能少

每次 fetch 都要做一次 `storage.get`：

```ts
// 若系统其实只关心 Health，别顺手把一大堆组件都 fetch 出来：
params(Query(Health, With(Enemy), With(Awake), Without(Player))).system((rows) => {
  // 需要 Enemy 标签？把它当 filter 而不是 fetch
});
// ✓ 上面 With/Without 只做存在性校验，不拉值，成本低
```

### ⑥ 把"瞬时事件"放事件通道，别污染组件

每 tick 清空的事件天然适合信号传递；如果把"被打了一下"写进组件再靠别的系统清除，反而多出大量写标记 + Changed 过滤的无效扫描：

```ts
// ✓ 用事件传递一次性的"伤害""死亡""掉落"
writer.send(new DamageEvent(e, 10));

// ✗ 别用组件当"一次性信号旗标"反复 insert/remove
```

### ⑦ 大规模场景下预分配与对象池

组件实例是普通对象。反复 `spawn/despawn` 会触发 GC。对高频实体（子弹、粒子）：

- 用 `Commands` 批量生成/销毁（把结构变更集中到 Stage 边界）；
- 需要"回收复用"时，自维护**空闲实体池**：销毁时把组件重置后放回池子，而不是真 despawn；需要时从池里取出复用。

```ts
class Bullet { constructor(public x = 0, public y = 0) {} }

// 伪代码：空闲池用组件标记，配合系统每帧检测
class FreePooled {}
// 发射时：先遍历 Query(Bullet, With(FreePooled)) 取一个重置；没有才 spawn
```

### ⑧ 知道什么时候该用/不该用 Commands

- **需要立即拿到结果**（比如马上要用实体句柄）→ 直接用 `world.spawn()`；
- **批量/遍历中生成销毁** → `Commands` 延迟应用，避免遍历期改布局（也快，因为一次性刷）；
- Commands 本身有队列开销，别在热循环里为了生成单个实体绕一大圈——直接 `world.spawn()` 即可。

### ⑨ 事件/资源别在每帧误注册

- 事件类型**注册一次**（App 装配期），不要每帧 `initEvent`；
- `Single()` 每次是独立遍历，别放逐实体循环里；
- 需要复用查询时，把 `QueryEngine` 提到系统外（docs/04 手动部分），或依赖 params 的缓存。

## 何时开始优化

1. 先用自然的 `params().system()` 把功能写对；
2. 卡了再换成 `systemForEach` / `spawnWith` / 对象池；
3. 用 `examples/` / `benchmarks/` 里的基准方式量一下热路径再调。

> PureEcs 提供了 `benchmarks/*.mjs` 参考基准（在仓库中），可用来对比不同写法的量级差异。

## 一套健康的架构习惯（不只是性能）

| 习惯 | 收益 |
| --- | --- |
| 每个系统"想要的组件"就是它的文档 | 可读性、最小候选集 |
| 结构变更走 Commands；读逻辑与写结构分离 | 稳定遍历、确定性 |
| 事件只传"一次性事实"，资源存"持续状态" | 少踩 tick 清理的坑 |
| 系统按 Stage 分层（输入→逻辑→渲染） | 顺序可预期，易调试 |
| 插件按协议（资源/事件）解耦 | 可复用、可测试 |
| 需要缓存时用 Local，别用模块级变量 | 多实例 World 安全 |

## 小结

- 遍历优先 `systemForEach`（单查询、零分配），表达力场景用 `system()`；
- 批量创建优先 `spawnWith`；热实体用空闲池 + `Commands` 批量调度；
- SparseSet 的 swap-remove 意味着**别在回调外保留组件引用**，需要就拷贝值；
- 查询引擎已做"最小候选集 + storage 缓存"，把"筛选意图"交给 `Query`/`With`/`Without`，别手写全量 if；
- 把一次性信号放事件、持续状态放组件/资源，避免无效写标记与清理扫描。
